Proposal

A signed-in user has no way to manage their own account. The nav-user dropdown already shows a disabled "Profile · Soon" placeholder; this change makes it real.

Delivers: a single Profile modal from the nav-user dropdown — section 1 photo + display name, section 2 change password — plus a nullable users.avatar_file_id, UserDto.avatarFileId, and a Next rewrite proxy so an <img> can load the cookie-guarded file endpoint same-origin.

Out: no page (modal only) · no role field · no email change · no resize/crop · no cleanup of replaced avatar files (orphans accepted, repo precedent) · no session invalidation on password change (stateless JWT).

Architecture

Avatar display:
  nav-user <AvatarImage src="/api/files/{avatarFileId}">
     → Next rewrite /api/files/:id → NEXT_PUBLIC_API_URL/files/:id  (cookie forwarded)
     → FilesController.download → JwtAuthGuard → stream bytes

Writes (all JwtAuthGuard, req.user = current user):
  Profile modal
   ├─ name     → PATCH /users/me          → ProfileController → UsersService.rename → UserDto
   ├─ avatar   → PATCH /users/me/avatar    → ProfileController(FileInterceptor 5MB/img)
   │              → FilesService.store(file,userId) → UsersService.setAvatarFile → UserDto
   └─ password → POST  /users/me/password  → ProfileService.changePassword
                  → verifyPassword(current) | ProfileErrors.INVALID_CURRENT_PASSWORD
                  → hashPassword(new) → UsersService.setPasswordHash → {success:true}

Module graph:  ProfileModule → UsersModule, FilesModule   (leaf; no cycle)
